# ⚡ 币安合约网格交易机器人 (Binance Futures Grid Trading Bot in Rust)

基于 Rust 编写的高性能币安 USDⓈ-M 合约网格量化交易机器人，支持同时配置和运行 **SOLUSDC、BTCUSDT 等多个交易对**。配套独立 Web 监控与控制面板，支持 WebSocket 毫秒级行情推送、只做 Maker（Post-Only GTX）挂单、动态滑动窗口、网页直接在线配置策略以及内嵌 **SQLite 数据库持久化**。

---

## 🌟 核心特性

1. **无需配置文件，网页直接配置**：
   - 启动无需任何 `config.toml` 或环境变量文件，直接打开浏览器控制台即可配置所有参数。
   - 可在网页上随时修改：交易对（如 SOLUSDC）、网格间距（如 0.1）、每格金额（如 100 USDC）、买入窗口深度、卖出窗口深度、Post-Only Maker 挂单、运行模式（模拟盘 / 测试网 / 实盘）、API Key & Secret 等。
   - 点击「保存并立即生效」，策略引擎自动重新对齐和更新挂单。
2. **内嵌 SQLite 数据库数据持久化**：
   - 使用内置嵌入式 SQLite（`data/bot.db`），零外部数据库依赖。
   - 自动持久化保存策略运行配置、历史成交记录、币安已实现盈亏与手续费、网格循环统计等。
   - 重启后恢复配置、成交记录及机器人挂单元数据，并先与交易所对账；无法确认交易所状态时暂停新增实盘订单。
3. **安全管理员密码认证与引导初始化**：
   - **首次启动安全引导**：若数据库中无管理员密码，需要输入当前启动日志中的初始化码，再设置管理员密码（至少 6 位）。未完成初始化时实盘交易保持暂停。
   - **全站 API 与 WebSocket 鉴权**：所有敏感操作（参数配置、策略启停、挂单撤销、密钥信息）及行情推送均受 Bearer 会话 Token 保护，杜绝未授权访问。
   - **密码安全存储**：新密码使用 Argon2id；旧版 SHA-256 密码在正确登录后自动升级。
   - **在线会话管理**：会话 24 小时后失效，支持退出登录和修改密码；登录尝试有频率限制。
4. **Maker 单（Post-Only GTX）**：
   - 使用 `timeInForce: "GTX"`，只以 Maker 方式挂单；拒单后先对账再更新窗口。
   - 具备自动价格检查与防穿仓拒单重试机制。
5. **严格的币安精度规则适配**：
   - 自动在启动时向币安查询 `exchangeInfo`。
   - 严格按币种的 `tickSize` 对价格规范化、按 `stepSize` 对数量截断，并严格校验 `minNotional`（最小下单金额），杜绝非法参数拒单。
6. **相邻网格与动态挂单窗口**：
   - 以 `0` 为固定锚点，买卖共用相邻档位，挂单窗口围绕**标记价格**移动。间距 `0.1`、标记价格 `111.86`、买卖窗口各 `3` 时，买单为 `111.8 / 111.7 / 111.6`，卖单为 `111.9 / 112.0 / 112.1`。标记价格本身不挂单；尚未取得标记价格时暂用最新成交价。
   - 最近一次已确认成交只用于避免立即在相同价格附近重复成交：新档位与该成交价至少相差一格。历史成交价不再锁定买单上沿或卖单下沿；例如此前买入 `110.2`，标记价格上涨到 `111.86` 后，买单仍会移到 `111.8 / 111.7 / 111.6`。遇到保留档位时跳过并补齐附近窗口，后续成交会更新保留档位。
   - 同价防护按交易对及运行模式分别从完整成交历史恢复，不受页面最近成交数量限制。同一订单的多次部分撮合仍计为一笔订单成交；升级前已挂出的订单和撤单期间发生的成交以交易所实际结果为准。
   - 不追踪开仓批次成本，不生成配对补单。成交后统一补齐当前窗口；每个普通单按配置目标金额和交易所数量步长向下取整，尾仓平仓单使用剩余可平数量。
   - 仅使用 Post-Only GTX 挂单，提交前仍用最新成交价检查买卖方向，拒单后重新对账，不降级为吃单。间距必须是交易所价格步长的正整数倍，不支持的配置会在撤单前被拒绝。修改间距会围绕标记价格重新计算相邻档位。
   - 所有未成交订单都遵守当前窗口和方向规则，包括旧版止盈单和余量单。窗口内保留已有订单的排队位置，同方向同价重复单保留较早的一笔；窗口外和方向不符的订单先撤销并确认终态及期间成交，再补齐窗口。部分成交的原订单先核实和完成，不创建同价替代订单。
   - 每个交易对可独立选择「做多 / 做空」，默认做多，旧配置自动按做多读取。做多时买入开仓、卖出平仓；做空时卖出开仓、买入平仓。开仓单受已持仓与未成交开仓单的合计敞口上限限制；平仓单只使用已有对应方向的仓位，扣除其他平仓单预留数量，并以 `reduceOnly=true` 仅减仓方式提交。价格范围、最近成交价和仓位限制可能使挂单数量少于窗口配置。
   - 策略参数可勾选「达到最大持仓名义价值时暂停策略」（默认关闭，需填写最大持仓上限）。持仓数量绝对值 × 标记价格达到或超过上限时，暂停整个策略并撤销机器人挂单，保留持仓；未取得行情标记价格时依次使用持仓标记价格、最新成交价。成交、行情更新及配置生效后均会检查。提交新开仓单前，还会按交易所步长取整后的完整开仓单数量检查成交后的预计持仓名义价值；若将超过上限，立即暂停，不提交该开仓单，也不缩量补齐。预计值刚好等于上限时允许挂单，持仓实际达到上限后暂停。未成交开仓单继续预留合计敞口，但仅因这些预留导致新增开仓单超限时只跳过新增开仓单，等待已有开仓单成交。暂停状态持久化，名义价值回落后不会自动恢复；手动恢复时若仍达到上限或下一笔开仓单将超限，会再次暂停。
   - 剩余仓位满足最小数量和金额时，在当前允许的平仓档挂一笔余量单（做多为卖单，做空为买单）。明确标记的余量可以合并，小额追加最多每 30 秒更新一次；合并目标同样遵守标记价格窗口和同价防护，不使用开仓成本定价。
   - 余量合并先撤单、核实期间成交、刷新仓位，再按持久化计划提交。响应丢失或重启时先查询固定订单 ID；已接受的目标继续核实，查询不确定时阻止新增订单。确认未接受且目标已不符合当前窗口、方向或最近成交价限制时，结束旧计划并重新补窗口。
   - 旧版配对意图只用于恢复可能已经接受的交易所订单；确认不存在的旧意图不再提交。历史配对价差与循环统计保留，新窗口成交只更新实际成交及盈亏统计。
   - 切换做多 / 做空前必须先平掉当前持仓。保存时先核实空仓、撤销并对账旧方向挂单，再次确认空仓后才切换；撤单期间若发生开仓成交，保留原方向并暂停。已有持仓方向与配置不一致时也会暂停并撤销机器人挂单。
   - 测试网和实盘仅支持币安**单向持仓模式（One-way / BOTH）**，检测到双向持仓模式会拒绝交易。机器人不会替用户切换账户持仓模式。[币安下单接口说明](https://developers.binance.com/docs/derivatives/usds-margined-futures/trade/rest-api/New-Order)中规定 `reduceOnly` 不适用于双向持仓模式。
   - 相邻网格和连续同价限制不保证盈利，多头平仓可能低于历史持仓成本，空头平仓可能高于历史持仓成本。
7. **独立的实时 Web 控制台**：
   - `frontend/` 使用 React、TypeScript、Ant Design、TanStack Query 和 Recharts；Rust 后端只提供 API 与 WebSocket。开发时 Vite 代理 API，生产环境由 Nginx 托管静态资源并转发请求。
   - 策略总览支持交易对搜索、状态和模式筛选、卡片操作与批量启停。实盘及测试网共享账户按最新快照去重，模拟账户按独立账户求和；筛选不影响账户汇总。
   - 交易对详情展示行情、持仓、盈亏、订单、成交和日志，以及今日成交和网格深度图。详情通过 WebSocket 更新，断流后通过 HTTP 自动刷新；超时数据会提示，暂停和撤单仍可使用。
   - 策略、全局连接及 Telegram 设置使用独立表单。离开未保存的表单或还原修改时会提示；实盘恢复、切换实盘配置、重建网格、撤单和清理历史均需确认。
   - 暂停或撤销机器人挂单会停止自动补单；恢复运行后重新对账并补齐网格。
8. **三种运行模式灵活切换**：
   - **Paper Trading（模拟盘 / Dry-Run）**：默认开启，实时订阅币安真实 WebSocket 行情，在本地内存中进行毫秒级撮合与收益统计，无需提供 API Key 即可零风险体验策略。
   - **Testnet（测试网）**：使用币安合约测试网 API 与资金进行联调。
   - **Live（实盘）**：连接币安合约主网执行真实真金白银挂单。
9. **全套 Docker 容器化与 GitHub Packages 支持**：
   - 包含多阶段构建 `Dockerfile` 与 `docker-compose.yml`。
   - 配置 GitHub Actions 自动化 CI/CD，自动编译多架构镜像发布后端和前端镜像至 GitHub Packages（`ghcr.io/zuoban/binancebot` 和 `ghcr.io/zuoban/binancebot-frontend`）。
10. **Telegram 通知**：在网页配置 Bot Token、Chat ID 并启用后，每笔确认成交的标题按“方向｜成交均价｜数量｜成交金额｜当天序号｜本小时序号”显示，成交均价取该订单成交记录中的均价，保留 4 位小数。序号按北京时间当天 00:00 起和成交所在小时分别统计，买单、卖单分开计数。同时展示账户权益、人民币估值、成交后的持仓金额、可用保证金及占比，平仓单附已实现盈亏（做多为卖单，做空为买单）。持仓金额按持仓数量绝对值 × 标记价格计算，以计价资产显示并保留 2 位小数；没有标记价格时暂用最新成交价，持仓或估值价格暂不可用时显示 `--`。策略启动、手动恢复及暂停时也发送通知，包含交易对、运行模式、原因和北京时间；达到最大持仓名义价值等自动暂停同样通知。重复暂停不重复发送，刷新网格或配置更新时的临时停单不通知。通知异步发送，失败记录日志。模拟盘、测试网及实盘均支持。

## 🐳 Docker 部署

### 1. 使用 Docker Compose 启动

无需创建配置文件，直接运行：

```bash
docker compose up -d --build
```

打开控制台并完成管理员初始化，在「策略参数」页面填写交易对、网格参数和运行模式，点击「保存并立即生效」。API 密钥和 Telegram 通知在独立的「全局配置」页面保存。设置会存入 SQLite；后续启动继续使用页面保存的设置。

程序只从 SQLite 读取策略配置。旧的 `config.toml`、`.env`、`BINANCE_*`、`GRID_*`、`TELEGRAM_*`、`PAIR_*`、`TRADING_PAIRS` 和 `SERVER_*` 环境变量不再读取，也不再支持 `--config`、`--symbol`、`--interval`、`--amount`、`--buy-window`、`--sell-window`、`--live` 或 `--testnet`。升级前已保存到数据库的配置继续保留；旧的单交易对数据库会自动转换为页面可管理的交易对列表。

首次启动提供 SOLUSDC 模拟盘默认参数，不需要 API 密钥。在「策略参数 → 交易方向」选择「做空」并保存，即可运行卖出开仓、买入平仓的空头网格；各交易对的方向独立保存。添加其他合约时，请在页面中选择与该合约价格步长相符的网格间距；新增交易对默认暂停，需检查配置后手动恢复。

前端容器对外映射 `8080:80`；Compose 启动后端时固定监听容器内的 `0.0.0.0:8080`，不修改数据库中保存的监听配置。前端通过 Docker 内部 DNS 动态解析后端地址，后端容器重建后可自动恢复连接。独立运行后端时仍可使用 `--host` 和 `--port` 指定监听地址和端口；日志级别可通过 `RUST_LOG` 调整。

启动后在浏览器打开控制台：
👉 **http://localhost:8080**

所有策略配置在页面上填写保存后，会自动存储在 `./data/bot.db` 中。

首次设置密码时，从 `docker compose logs binance-bot` 找到“初始化码”，输入到网页初始化表单。直接运行二进制时，初始化码显示在程序启动日志中。

首次使用实盘时机器人默认暂停，需在控制台确认配置后手动恢复。暂停状态会写入数据库，重启后继续保持暂停。

实盘远程访问请在 HTTPS 反向代理或受控 VPN 后使用控制台；不要把 HTTP 端口直接开放到公网。API 凭证保存在 `data/bot.db`，请限制该文件的访问权限并做好备份。

同一账户、同一交易对请只运行一个本程序实例。机器人目前用 `gb_` 订单前缀识别自己创建的订单，多个实例会相互识别并可能撤销对方订单。

收到 Ctrl+C 或 SIGTERM（例如 `docker compose stop`）时，程序立即禁止新增订单和恢复策略，保存暂停状态，再撤销并核实机器人挂单，保留持仓。正常停机最多等待策略清理 30 秒、Web 服务退出 5 秒；Compose 已设置 45 秒停机宽限。直接使用 `docker run` 时建议添加 `--stop-timeout 45`。清理失败或超时会返回错误并保留订单恢复元数据，下次启动保持暂停并重新对账，需核实挂单后手动恢复。

交易所返回执行结果未知（包括 `-1006`、`-1007` 和不确定的服务端错误）时，机器人保留原订单 ID，停止新增订单并等待对账。只有尚未确认接受的订单意图，在创建至少 30 秒后仍被交易所明确查询为不存在，才会释放预留；查询失败和已有交易所订单 ID 的订单不会按此规则清理。

最新成交价超过 15 秒未更新，或已有标记价格超过 15 秒未更新时，暂停新增普通单和余量单，也不根据过期行情移动挂单窗口。数据恢复且账户、订单对账有效后继续维护窗口；尚未取得标记价格时可使用有效的最新成交价。已有挂单仍可能在交易所成交，后台继续对账，手动暂停和撤单仍可使用。

每个交易对通过一条 `/market` WebSocket 组合连接接收成交价与每秒标记价格。成交价或标记价格缺失或至少 8 秒未更新时，下一次同步周期尝试通过 REST 补取；失败后按交易对及行情类型分别退避，成功或收到有效推送后重置。行情兜底使用较低的本地请求预算上限，给周期账户、持仓和挂单对账留出空间；持续高负载下，行情兜底仍可能被延迟。请求失败不会刷新行情时间，同步周期较长或发生网络延迟时，REST 兜底可能晚于 15 秒，过期保护仍会阻止新增订单。行情时间依赖本机时钟，需保持系统时间同步；明显过旧或超前的推送会被丢弃。

标记价格 REST 兜底在同一交易所地址的 10 秒内有至少 10 个不同交易对请求时，会共享全市场标记价格快照；请求开始时间作为行情时间，主网和测试网分别缓存。共享请求失败会短暂冷却，等待同一请求超过 100 毫秒的交易对会继续后续对账并按退避规则重试。快照没有对应交易对时使用单对请求。该优化降低多对断流时的标记价格请求量，但不保证在预算长期耗尽时每个交易对都能获得行情。

### 2. 使用预构建镜像

发布后的两个镜像均需要。使用仓库内的 Compose 配置运行：

```bash
docker compose pull
docker compose up -d
```

后端镜像本身只提供 API，单独运行后端容器不会提供网页。前端通过同源 `/api`、`/ws` 代理连接后端，生产反向代理必须支持 WebSocket Upgrade，并将所有前端路由回退到 `index.html`。

## 🛠️ 本地编译与运行

### 1. 运行环境
- Rust 1.88+（使用 `cargo`）
- Node.js 22.12+ 和 npm（用于前端开发与构建）

### 2. 编译与运行

#### 分别启动后端和前端

在两个终端分别执行：

```bash
# 后端：自动初始化 SQLite 并以模拟盘模式运行
cargo run --release
```

```bash
# 前端：开发服务器将 /api 和 WebSocket 代理到 127.0.0.1:8080
cd frontend
npm ci
npm run dev
```

打开 Vite 输出的地址（默认 `http://127.0.0.1:5173`），完成管理员初始化。若后端监听其他地址，在启动前端时设置 `API_PROXY_TARGET`，例如 `API_PROXY_TARGET=http://127.0.0.1:18080 npm run dev`。生产构建使用 `npm run build`，生成的 `frontend/dist` 由前端容器的 Nginx 提供。

在「策略参数」页面调整参数并保存后，策略引擎实时热更新。

### Telegram 通知

1. 在 Telegram 使用 @BotFather 创建 Bot，复制 Bot Token。
2. 给 Bot 发送一条消息；打开 `https://api.telegram.org/bot<Bot Token>/getUpdates`，从返回内容中的 `message.chat.id` 获取 Chat ID。群组通知需先将 Bot 加入群组并获取该群组的 Chat ID。
3. 在网页「全局配置」页面填写 Bot Token 和 Chat ID，勾选「启用 Telegram 通知」，点击「保存全局设置」。Bot Token 不会在网页回显；留空可保留已保存的 Token。

所有交易对共享这组通知设置，配置会存入 SQLite，关闭开关即可暂停全部交易对的通知。页面支持清除已保存的 Telegram 凭证；清除前需关闭通知。

#### 指定数据库路径或临时监听地址

```bash
cargo run --release -- --db data/my_bot.db
# 监听参数仅作用于当前进程
cargo run --release -- --host 127.0.0.1 --port 8080
```

## 多交易对配置与运行

每个交易对有独立的网格引擎、行情订阅、挂单、持仓、累计统计、日志和启停状态。所有交易对共享一个 Web 控制台、管理员登录和 SQLite 数据库；某个交易对初始化失败、行情中断或达到持仓上限时，只暂停该交易对。

1. 在「策略总览」点击「新增交易对」，填写合约代码、网格间距、每格金额、买卖窗口和运行模式。
2. 点击「保存并添加」。该交易对立即出现在顶部选择器中，策略保持暂停；检查参数后点击「恢复」。每个新增交易对使用独立的默认网格参数，并自动共享全局连接与 Telegram 通知设置。
3. 使用顶部选择器切换交易对，再保存各自的参数。网格和运行模式按交易对独立保存；API 凭证、请求有效窗口、同步间隔和 Telegram 通知在独立的「全局配置」页面统一配置，点击「保存全局设置」后应用于所有交易对。重启不会被配置文件或环境变量覆盖。
4. 移除交易对时，先暂停策略并等待挂单撤销完成，再在策略参数中点击「移除交易对」。系统再次核实撤单后移除引擎，已有持仓、成交历史、统计及恢复元数据保留；至少需要保留一个交易对。需要更换合约时，添加新的交易对后再移除旧的交易对。

- 同一实盘账户内的交易对共用账户保证金，页面的账户权益不能按交易对相加；持仓上限按每个交易对分别计算。模拟盘为每个交易对提供独立的模拟账户。
- API Key、API Secret 和 Telegram Bot Token 不会明文回显。留空密钥输入框保留已有值；勾选「清除已保存的 API Key 和 Secret」仅当所有交易对均处于模拟盘模式时可清除全局凭证。
- 旧版本的交易对连接与通知配置会在启动时自动迁移，以列表中的第一个交易对为全局配置基准；若原先各交易对使用不同设置，升级后请在「全局配置」中核对。
- Ctrl+C / SIGTERM 会立即阻止全部交易对新增订单，并同时撤销和核实各交易对的机器人挂单、保存独立暂停状态，保留持仓。

所有接口与 WebSocket 仍需管理员认证：

| 接口 | 作用 |
| --- | --- |
| `GET /api/pairs` | 列出全部交易对、运行状态、模式和网格摘要 |
| `GET /api/overview` | 一次获取全部交易对的完整快照及生成时间，用于看板独立刷新 |
| `POST /api/pairs` | 保存并添加交易对，初始暂停 |
| `DELETE /api/pairs/{symbol}` | 移除已暂停且挂单已清理的交易对，请求体需含 `confirm: true` |
| `GET / POST /api/global/config` | 查看和修改所有交易对共享的交易所连接与 Telegram 通知设置 |
| `GET / POST /api/server/config` | 查看当前与保存的监听设置，保存后重启生效 |
| `GET /api/pairs/{symbol}/status` | 指定交易对的完整快照 |
| `GET /api/pairs/{symbol}/orders`、`/trades`、`/logs` | 指定交易对的订单、成交、日志 |
| `GET / POST /api/pairs/{symbol}/config` | 查看和在线修改指定交易对的网格与运行模式；全局字段请使用 `/api/global/config` |
| `POST /api/pairs/{symbol}/control` | 对指定交易对执行 `pause`、`resume`、`cancel_all`、`rebalance` |
| `/api/pairs/{symbol}/ws` | 指定交易对的快照、日志和控制通道，认证方式同 `/ws` |

原 `/api/status`、`/api/config`、`/api/control` 和 `/ws` 在多交易对模式下指向列表中的第一个交易对。数据库导出及历史清理仍为全局操作，历史清理会同步重置全部交易对的内存统计。

### 本地多交易对负载测试

下面的命令运行独立的模拟盘突发负载测试，不连接交易所，也不读取或修改现有数据库：

```bash
BENCH_PAIRS=50 BENCH_ROUNDS=6 cargo test --release --lib simulated_pair_burst -- --ignored --nocapture
```

`BENCH_PAIRS` 是合成交易对数量，`BENCH_ROUNDS` 是突发行情轮数（至少 2）。测试使用内存 SQLite 和 4 个 Tokio 工作线程，每轮同时处理所有交易对的合成行情、模拟成交和网格维护；最后并发生成一次全部交易对的快照。输出包括初始化时间、单交易对处理耗时的 p50/p95/p99、每轮总耗时、快照耗时和模拟成交数。单交易对耗时从其任务开始执行时计时，排队时间体现在每轮总耗时中。

该测试用于比较代码或机器之间的表现，不包括真实 WebSocket、网络、持久化磁盘、交易所限流、实盘下单和长时间运行，也不能直接换算安全的实盘交易对数量。生产容量还需要在目标环境逐步增加交易对，观察行情新鲜度、对账延迟、请求限流、CPU 和内存。

本地模拟交易所的同步路径测试可通过以下命令单独运行：

```bash
BENCH_PAIRS=30 BENCH_SECONDS=65 cargo test --release --lib simulated_live_reconciliation -- --ignored --nocapture
```

该测试使用暂停状态的实盘引擎、合成行情、内存 SQLite 和本地 HTTP 服务，每 3 秒模拟一次新鲜标记价格推送，并错峰执行实际的挂单、账户及持仓同步，共用缓存和本地请求预算。`cycles` 是完成的同步轮次，`orders_ok` 和 `account_position_ok` 分别是挂单对账、账户与持仓同步成功的轮次；`*_sent` 是模拟服务收到的请求数，`estimated_weight` 按当前代码的本地权重累计，并非交易所实测权重。新鲜标记价格下 `mark_sent` 应为 0，其余成功轮次在未触及限流时应与 `cycles` 相同。测试结束时还向模拟服务执行一次关键挂单查询和撤单请求，分别用 `emergency_list_ok`、`emergency_cancel_ok` 记录结果；该探测不计入周期请求数或估算权重。

该测试不会发送订单，模拟服务也不会主动返回 429，无法覆盖真实网络延迟、其他进程共享 IP、交易所响应头、活跃挂单与成交、磁盘数据库、行情连接或长时间稳定性。建议至少运行 65 秒，以覆盖本地 60 秒滚动权重窗口；实际生产容量仍需在目标环境验证。

可在同一测试中模拟所有交易对的行情推送在启动 6 秒后同时中断 40 秒，再恢复：

```bash
BENCH_PAIRS=50 BENCH_SECONDS=65 BENCH_OUTAGE_SECS=40 BENCH_FAIL_MARK=1 cargo test --release --lib simulated_live_reconciliation -- --ignored --nocapture
```

`BENCH_FAIL_MARK=1` 让模拟标记价格 REST 接口在断流期间返回 503；设为 `0` 则允许 REST 兜底。`ticker_sent` 和 `mark_sent` 分别统计模拟服务收到的成交价和标记价格请求，其中 `mark_bulk_sent` 是全市场标记请求数，其余为单对请求；估算权重分别按 10 和 1 计。`outage_fresh`、`outage_stale` 统计断流期间同步后行情有效和过期的次数，`recovery_fresh` 统计恢复推送后行情有效的次数。这些次数是同步轮次，不是交易对数；模拟引擎处于暂停状态，不发送真实订单。

一轮本机测试的数据及适用范围见 [多交易对容量测试记录](docs/multi-pair-capacity.md)。

## 💾 数据库存储说明 (`SQLite`)

机器人的所有状态与数据自动保存在 SQLite 数据库中（默认路径 `data/bot.db`）：

- **`app_config` 表**：存储当前生效的交易所参数、网格间距、下单金额、滑动窗口、风控范围与 API 凭证。
- **`trades` 表**：记录每笔已确认成交的价格、数量、运行模式、币安实际已实现盈亏、报价资产手续费及核实状态。尚无法核实的记录显示“待同步”，不计入已实现盈亏汇总。升级前的成交标为 `UNKNOWN`，不会自动归入模拟盘、测试网或实盘。
- **`scoped_grid_stats` 表**：按交易对及运行模式分别累计成交量、成交笔数、已完成网格循环次数及配对价差估算。当前模式的已实现盈亏与手续费从同一范围的 `trades` 记录汇总；原 `grid_stats` 表保留旧版历史数据。
- **`managed_orders` 表**：保存机器人挂单及配对元数据，供重启对账使用。
- **`pair_intents` 表**：保留旧版恢复元数据；升级后先查询交易所核实可能已接受的订单，确认不存在时结束旧意图，不生成新配对单。
- **`bot_runtime` 表**：单交易对配置继续同步运行或暂停状态，兼容旧版本。
- **`pair_runtime` 表**：按交易对及运行模式独立保存启停状态，单交易对与多交易对配置均优先读取该表，缺失时兼容旧状态。在线切换运行模式时，配置与当前启停状态在同一事务中保存，重启后保持暂停状态。

已实现盈亏统计仅覆盖本程序保存的已确认订单，扣费后金额扣除同一报价资产的成交手续费；资金费和手工交易不计入。

任何 SQLite 客户端（如 `sqlite3`, DBeaver, TablePlus）均可直接打开 `data/bot.db` 查阅和导出交易数据。

### 在线导出分析数据库

登录控制台后，打开「成交历史」，点击「导出数据库」，下载带北京时间戳的 `binancebot-analysis-YYYYMMDD-HHMMSS.db` 文件。导出覆盖全部交易对与运行模式的完整成交记录、策略配置、机器人订单、配对补单意图、余量合并计划和统计，不受页面最近 50 条成交的限制。

导出使用 SQLite 一致性快照，包含已提交的 WAL 数据，无需暂停策略或手工复制 `.db-wal`。副本中的 Binance API Key / Secret、Telegram Bot Token / Chat ID、管理员密码哈希和登录会话均被移除，原数据库保持不变。文件用于离线分析，不是包含凭证的恢复备份；系统运行日志仅保存在内存中，不包含在数据库导出里。

接口为 `GET /api/database/export`，须携带有效的管理员 `Authorization: Bearer <token>`；成功返回 SQLite 附件，失败返回 JSON 错误。

### 清理历史交易记录

在「成交历史」点击「清理历史记录」，确认后删除**全部交易对及运行模式**的历史成交记录（包括旧版 `UNKNOWN` 记录），并重置累计成交笔数、成交量、已实现盈亏、手续费和历史循环统计。页面列表及今日成交图同步更新，之后的新成交从零开始累计。清理无法撤销，建议先导出数据库保存。

清理保留当前持仓、账户余额、挂单、配置和登录信息，策略可继续运行。数据库仅保留必要的已处理成交 ID 和各交易对、模式的最近成交边界，供订单防重复入账和重启恢复使用；清理不会删除币安交易所的成交记录，也不承诺立即缩小 SQLite 文件大小。

接口为 `POST /api/trades/clear`，须携带有效的管理员 `Authorization: Bearer <token>` 和 JSON 请求体 `{"confirm":true}`。成功返回删除笔数及最新页面快照；未确认返回 `400`，未登录返回 `401`，清理失败返回 `500`，事务失败时保留原数据。

## 🌐 远程服务器访问排查指南

如果在远程服务器（阿里云、腾讯云、华为云、AWS EC2、GCP 等）部署后，在本地电脑浏览器访问 `http://<服务器公网IP>:8080` 提示「无法访问此网站」或「连接被拒绝 (Connection Refused)」，请按以下步骤排查：

### 1. 检查云厂商控制台「安全组 / 防火墙」规则（最常见原因 90%）
云服务器默认通常只开放 22 端口（SSH），需要手动放行 `8080` 端口：
- **阿里云 ECS / 轻量应用服务器**：控制台 -> 安全组 -> 入方向规则 -> 添加规则 -> 协议选择 `TCP`，端口范围填 `8080`，授权对象填 `0.0.0.0/0`。
- **腾讯云 CVM / Lighthouse**：控制台 -> 防火墙 / 安全组 -> 添加规则 -> 来源 `0.0.0.0/0`，协议 `TCP`，端口 `8080`，策略 `允许`。
- **AWS EC2**：Security Groups -> Inbound rules -> Edit inbound rules -> Type: Custom TCP, Port: `8080`, Source: `0.0.0.0/0`。

### 2. 检查服务器内部 Linux 系统防火墙
部分 Linux 发行版内置防火墙可能会拦截非标准端口：
```bash
# Ubuntu / Debian (UFW 防火墙)
sudo ufw status
sudo ufw allow 8080/tcp
sudo ufw reload

# CentOS / RHEL / Alibaba Cloud Linux (Firewalld 防火墙)
sudo firewall-cmd --zone=public --add-port=8080/tcp --permanent
sudo firewall-cmd --reload
```

### 3. 在服务器本地测试服务是否正常运行
登录服务器终端，执行命令测试本地回环是否可以正常响应：
```bash
curl -I http://127.0.0.1:8080
```
如果返回 `HTTP/1.1 200 OK`，说明机器人服务本身运行完全正常，外部无法访问必为第 1 步或第 2 步的**安全组/防火墙**未开放。

### 4. 检查 Docker 端口映射与监听地址
若使用 Docker 部署，请确保：
```bash
docker ps
```
查看前端容器的 `PORTS` 列是否显示为 `0.0.0.0:8080->80/tcp` 或 `:::8080->80/tcp`。
*(切勿写成 `-p 127.0.0.1:8080:8080`，否则只允许服务器本地回环访问)*
