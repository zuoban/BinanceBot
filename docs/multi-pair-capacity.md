# 多交易对本地容量测试记录

## 2026-11-13：后端优化后的回归基线

本节供后续优化对比用，仅为本机合成场景，不能换算实盘容量。运行方式：

```sh
BENCH_LOOP_ROUNDS=10 BENCH_LOOP_DELAY_MS=250 \
  cargo test --locked --lib --release \
  event_loop_latency_benchmark::control_during -- --ignored --nocapture
```

10 轮、250 毫秒本地 HTTP 延迟、4 个运行时工作线程、内存数据库，样本少，
p95 接近最大值：

| 指标 | p50（毫秒） | p95（毫秒） |
| --- | ---: | ---: |
| 控制命令入队到确认 | 0.416 | 0.734 |
| 标记价格推送到引擎观察 | 2.395 | 5.263 |

同一测试在上一节记录中的标记价格推送 p95 为 5.856 毫秒，本次未出现回归。

本轮后端改动：

- 广播落后现在计入 `/metrics`：`binance_bot_broadcast_lagged_total{channel="ticker"}`
  和 `{channel="websocket_client"}`。该计数持续上升说明同步周期过长或客户端过慢。
- WebSocket 广播容量从 100 提高到 256；同时落后的客户端在 250 毫秒内共用同一份
  重同步快照，强制广播会使该缓存失效。
- SQLite 读连接数按可用核数取 2 到 8；`run_blocking` 最多同时运行 32 个任务，
  超出的在异步侧等待，不会占用阻塞线程，也不会拒绝写入。
- PnL 补偿的每分钟权重预算在同时需要补偿的交易对之间平均分配；单个交易对仍可
  使用全部预算，每个交易对在窗口内的第一次请求不受份额限制。

提交路径；交易所请求仅连接本地模拟服务，数据库均为独立内存数据库。

补偿场景的订单查询全部返回交易所“订单不存在”，未进入成交明细接口；修复后
仍保留全部待核实记录。独立程序另核对了取消等待提交锁的验证不会迟到提交、
退休实例拒收新验证，以及已受理的验证即使调用方取消，仍在状态移交前完成
数据库提交、手续费及最近成交缓存发布。

710 项后端测试通过，4 个显式基准默认跳过；格式检查、Clippy 和前端生产构建
通过。另行执行 10 轮、250 毫秒行情延迟基准，控制确认均在模拟 HTTP 响应仍被
持有时完成。该基准不测量实盘撤单耗时，以上结果也不能用于推算实盘容量。

## 2026-11-07：交易链路和控制台优化

以下为本机合成场景及隔离数据库、模拟盘页面的实测，不能换算实盘容量。行情延迟
场景为 10 轮、250 毫秒本地 HTTP 延迟、4 个运行时工作线程；配置确认必须在模拟
服务仍持有响应时完成。小样本的 p95 接近最大值，调度和机器负载会影响结果。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 行情请求期间配置确认 p95（毫秒） | 311.340 | 12.914 |
| 标记价格推送到引擎观察 p95（毫秒） | 7.346 | 5.856 |
| 十万条历史中查询待核实成交的中位耗时（毫秒） | 80.181 | 0.033 |
| 连接失败入口实际请求的 JS 总量（字节，未压缩） | 1,359,729 | 868,272 |
| 2 对集中成交的持仓 HTTP 请求数（含全市场查询） | 13 | 9 |
| 同场景账户 HTTP 请求数 | 12 | 7 |

SQLite 对比使用同一个已升级的十万条成交数据库，其中三笔待核实；分别强制原
作用域索引和新增部分索引，预热后交替测量 21 次，结果逐条一致。正常查询计划
使用新增部分索引。旧数据库升级还核对了历史小时回填、精确盈亏、待核实数量及
完成标记；十万条历史均保留。首次升级需回填和建索引，后续重启不重复回填。

前端数值按实际连接失败入口的请求列表统计，图表依赖已移出该入口；打开详情时
按需加载图表。当时测试构建仍提示一个共享 JS 文件超过 500 kB（513.88 kB，未调整
警告阈值）；后续已通过 `manualChunks` 拆分依赖消除该警告，且未上调 500 kB 阈值。浏览器还验证了总览摘要与完整详情、两个账户订阅收到相同
采集帧、设置页停止总览轮询、旧账户帧不延后 HTTP 补取，以及有效推送恢复后
停止补取。

集中成交均使用本地交易所、暂停的实盘引擎和虚构凭据，每对初始 16 单、执行两轮：

| 场景 | 每对每轮成交 | 挂单对账成功 / 总数 | 普通账户同步成功 / 总数 | 持久化成交 | 已核实盈亏 | 待核实盈亏 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 对，内存数据库 | 2 | 6 / 6 | 6 / 6 | 8 | 8 | 0 |
| 50 对，磁盘数据库 | 4 | 150 / 150 | 100 / 150 | 400 | 0 | 400 |

终态成交按交易对及观察批次刷新账户和持仓，再提交全部成交。并发交易对的新
成交仍会使在途风险读取失效并重试，因此 HTTP 次数可能超过批次数；不能删除
这些新鲜度重试来凑请求计数。50 对场景有两次本地权重拒绝，随后普通账户读取
进入共享冷却；PnL 补偿也因普通预算不足未发出明细请求，全部成交保留待核实。
该场景核对了剩余挂单及成交持久化，未等待后续预算窗口，不能据此声称积压已清空。

最终验证包括后端 702 项测试、前端 227 项测试、Rust 格式与 Clippy、前端生产
构建。显式基准另行运行；数据库汇总失败回滚、重复成交、PnL 补核实、历史清理、
风险刷新失败恢复、暂停竞态和行情旧代响应均有对应回归覆盖。

## 2026-10-28：共享标记价格兜底后

与下一节使用相同的 50 对、65 秒本地模拟，推送中断 40 秒后恢复。10 秒内至少
10 个不同交易对请求标记价格时改用全市场快照；快照缓存最多 3 秒，保留请求开始
时间。全市场请求按权重 10、单对请求按权重 1 计。等待共享请求超过 100 毫秒
的引擎继续对账并按原退避策略重试。共享快照按交易所地址隔离。压测结束后补充了
防止请求时间早于已有标记行情的保护，并通过完整测试；没有重跑这两组压测。

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 正常 | 1084 | 1058 | 1069 | 13（4） | 196 | 667 / 0 | 317 |
| 503 | 1084 | 1053 | 1052 | 16（7） | 181 | 201 / 466 | 317 |

## 2026-10-28：调整优先级前的本地模拟对账

在 Apple M1、16 GiB 内存机器上，使用 Rust release 构建运行
`simulated_live_reconciliation`。每组执行 65 秒，4 个 Tokio 工作线程；
使用独立的内存 SQLite、本地 HTTP 模拟服务和虚构凭证。每个交易对处于暂停状态，
使用合成行情并按固定的均匀偏移每 3 秒执行一次真实的实盘同步逻辑。所有交易对
共享账户缓存、持仓缓存和本地请求权重限制器。模拟服务始终返回成功且不存在挂单，
不返回 429，也不模拟成交。

| 交易对 | 同步轮次 | 挂单对账成功 | 账户及持仓同步成功 | 标记价格请求送达 | 总请求权重 | 同步耗时 p95 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 30 | 650 | 650 | 650 | 650 | 1910 | 2.12 ms |
| 31 | 672 | 672 | 663 | 670 | 1952 | 1.80 ms |
| 32 | 694 | 694 | 647 | 660 | 1954 | 1.82 ms |
| 50 | 1084 | 1084 | 698 | 695 | 2189 | 1.43 ms |

总请求权重按服务收到的请求及当前客户端中配置的权重相加，覆盖整个 65 秒，
不能直接与每分钟额度比较。耗时从同步逻辑开始执行起计，不含定时器调度延迟；
请求被本地快速拒绝时耗时会降低，因此不同失败率下的 p95 不能直接比较。
`/usr/bin/time -l` 记录的最大常驻内存分别约为 20.2、19.7、20.7 和 23.7 MiB，
包括测试框架和模拟服务，不能视为生产进程的内存用量。

在这一轮特定场景中，30 对是已测试且所有同步均成功的最大规模；31 对开始
出现账户及持仓同步失败，32 和 50 对失败更多。由于只运行一轮、使用固定偏移
且无其他 IP 流量，30 对不代表可安全用于实盘的上限，也不保证其他环境同样成功。
本次测试时日常挂单列表查询使用关键请求预算，这使其在普通预算耗尽后仍可能成功，
但也可能挤占需要给撤单等关键操作保留的容量。

真实 WebSocket 连接与消息、交易所延迟、响应头及限流、活跃挂单、下单、
成交、磁盘数据库、重新连接以及长时间运行都不在本次测试范围内。生产容量
应在目标环境使用真实工作负载逐步验证，同时观察行情新鲜度、对账成功率、
请求拒绝、CPU、内存和撤单能力。

测试方法和参数见 [README](../README.md#本地多交易对负载测试)。每组至少运行
65 秒以覆盖一个完整的 60 秒本地滚动窗口；更长的运行时间可以通过
`BENCH_SECONDS` 设置。
